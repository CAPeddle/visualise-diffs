<objective>
Prove that a misbehaving sidecar cannot hang, flood or poison a run: timeout, stdout cap, stderr drain, non-zero exit, malformed and wrong-schema responses, and a child process that is really killed.

Purpose: plan 01-02 implemented the bounds (T-01-05); this plan proves them with a fake sidecar and adds the one operational setting the proof needs, the timeout override (TRC-01 robustness, TRC-02 failure mapping from ADR-001: a sidecar failure is a tool failure, not a silent partial result).

Fix budget (bounds the open-ended part): production code may change only to fix a defect a test here exposes, only in the two source files in `files_modified`, plus the timeout override; all changes together at most 80 lines. A defect that needs more, or a file elsewhere, is recorded in the summary under Deviations with the failing test name; never loosen a limit to pass.

Wave-3 ownership rule: plans 01-04, 01-06, 01-07 and 01-08 run in parallel. Do not edit files they own (`Cli/**` and `Git/**` belong to 01-04; `extractors/**` to 01-06; `Scope/**`, `Model/**`, `Diff/**` to 01-07; `Output/**` to 01-08). Do not edit `tests/Vdiff.Tests/Support/*`.

Test rule: every test class in this plan that reaches the real sidecar (any use of `CliApp.Run` or of `CppSidecar.Extract` with the real binary) or sets process-wide environment variables carries `[Collection("sidecar")]` (defined in plan 01-03), so xunit runs those classes one at a time after the fixture's cargo build.

  <files>

  <behavior>
    - `hang` (timeout 3 s) fails within about 10 s with a message naming the timeout, and the child process is gone afterwards.
    - `flood-stdout` (cap 1 MiB) fails naming the output cap, with memory use bounded by the cap.
    - `flood-stderr` (8 MiB on stderr, then a valid response) succeeds, the stderr tail is bounded to its cap.
    - `exit3` fails and the message carries the stderr tail, never file content; `garbage`, `truncated` (half a JSON object) and `wrong-schema` fail; `ok-empty` (a valid response with no files) succeeds.
    - A child that ignores its input and exits at once (`ok-empty` sent a large manifest) does not deadlock the writer: the call completes.
  </behavior>
  <action>
Create `tests/Vdiff.FakeSidecar`, a net10.0 console project added to `vdiff.sln` and referenced by `Vdiff.Tests.csproj`. Its mode comes from the FAKE_SIDECAR_MODE environment variable, so it can also be selected through VDIFF_CPP_TS (which can only name an executable); it writes its own process id to the file named by FAKE_SIDECAR_PID_FILE so a test can confirm the child was killed (T-01-05, T-01-29). Confirm the referenced project's apphost executable lands in the test output folder; if it does not, compute its path from the test assembly directory. Add `SidecarBoundsTests` calling `CppSidecar.Extract` with a `SidecarCommand` for the fake and tiny `SidecarLimits`. Where a test exposes a defect (a limit not enforced, a child left alive, a deadlock on large stdin), fix it in `BoundedProcess.cs` or `CppSidecar.cs` within the fix budget and note it in the summary.
