<objective>
Close the single gap of `01-VERIFICATION.md` (status gaps_found, 43/47): review finding CR-01. `HeldDirectory.SplitAtDeepestExisting` (introduced by plan 01-16) trims the trailing separators of the typed directory before it tests whether the path exists, so `--out C:\` becomes `C:`. On Windows `C:` is not the root; it is the process's current directory on drive C. The held directory is therefore the current directory, the five files land there, and stdout says `vdiff: wrote 5 files to C:\` with exit 0. The first half of SC2 holds (the repository is not changed; the held directory's final path is still judged), but the literal clause "everything the run writes lands in the given output directory and nowhere else" is false for this input, and TRC-02's "in the output directory" with it. The product owner chose the fix-plan disposition over an override (`01-VERIFICATION.md` human_verification item 1).

Purpose: restore SC2 for a drive-root `--out`, pin the root rule from both sides (CLI and the trial script), and keep the repository-unchanged guarantee, the exit-code contract (R27) and every fixed text exactly as they are.

Output: a root-aware `SplitAtDeepestExisting`, ten new tests (seven unit cases: six theory rows and one fact; one `CliApp.Run` case; two script-parity cases), register and validation-map rows, one SUMMARY.

Decisions recorded in this plan (Claude's discretion; `01-CONTEXT.md` fixes only D-02, D-03 and D-09, which this plan honours; P-numbers are new):

- **P-1, the observable outcome of `--out C:\` (reversible).** The tool writes into the drive root as typed: exit 0 and the success line naming the typed path when the account may write there; exit 1 with the existing `vdiff: could not write the output: ...` line when it may not (the same two outcomes the tool had before plan 01-16). It does not refuse a root. A refusal would need a new fixed text, which is a contract change beyond the minimal fix, the operator typed the root on purpose, the success line already names the typed path (so "files in the typed path" makes it truthful again), and no new argument, reason or exit code is needed (D-03, R27). The existing final-path judgement still applies to a root, so a root that is or lies inside the analysed repository or a protected directory is refused with the existing text. Rated reversible: either outcome is one guard in one function; no migration, no consumer, no data. No checkpoint:decision.
- **P-2, the rule is "never trim below the root", not a bare length test.** The review's suggested fix (trim only when the path is longer than `Path.GetPathRoot`) leaves one input unfixed: `C:\/` and `C://` have root `C:\` (length 3) and total length 4 (probed on both PowerShell hosts at planning time), so they would still be trimmed to `C:`. The fix therefore trims as today and then starts from the root when the trimmed text is shorter than the root (a null root counts as empty). For every input `CliApp` can send the two forms agree: `CliApp.Run` passes `HeldDirectory.Create` the output of `FinalPath.Resolve` (read at planning time), which walks the full path segment by segment and returns the bare root with its separator (`C:\`, or the slash) for a root and a path without a trailing separator for anything else, so only the bare root reaches the trim. The stricter form also covers a root spelled with extra separators when `HeldDirectory.Create` is called directly, and the slash root of Linux and macOS (the old trim made it the empty string and failed with the fixed unresolvable text).
- **P-3, how the CLI case stays safe on a dev machine.** The test must not write five files into a real drive root, and it must not change the process's current directory (process-wide state; `[Collection("sidecar")]` serialises only within that collection and xunit runs other collections in parallel; a grep of `tests/` at planning time finds no xunit configuration file and no assembly-level attribute (CollectionBehavior, DisableTestParallelization and the like) that turns parallelism off). Instead: take the root of the drive that holds the process's own current directory (`Path.GetPathRoot(Directory.GetCurrentDirectory())`, never a literal `C:\`, because the defect only shows on the drive whose current directory is the one the drive-relative form resolves to). Run `CliApp.Run` with `--out` set to that root and a hook on the existing `AfterHeld` seam (it fires after the hold and before the first byte, with the directory every file would go to). The hook records the path and throws a test-local sentinel exception, so the run stops before any file exists; `CliApp` reports it as exit 1 and stderr `vdiff: unexpected failure (<exception type name>)`. The discriminating assertion is the recorded path: it equals the root after the fix and equals the process's current directory before it (the red run must show that). The "scratch current directory" the brief asks for is thus the test host's own current directory, which is already a directory that is not the root; a precondition assertion makes the test fail loudly if the host ever runs from the root itself. On Linux the pre-fix run fails with the fixed unresolvable text before the hook, so the hook never runs, which is also red.
- **P-4, how the script mirror is confirmed and pinned.** Read at planning time: the script does not trim a root (`Get-FullPath` trims only when the full path is longer than its root, and `Open-HeldDirectory` never trims, it walks up with `GetDirectoryName`), and a child-host probe on PowerShell 7 and Windows PowerShell 5.1 (functions extracted with the PowerShell parser, called on `C:\`, read-only) returned the root from both `Open-HeldDirectory` and `Get-FullPath`. So `scripts/trace-run.ps1` is unchanged by this plan. The parity is pinned by a test that runs on both hosts: a driver script written to a scratch directory at test time parses `scripts/trace-run.ps1`, defines every top-level function it finds, sets the five script-scope variables those functions read, calls `Open-HeldDirectory` on the drive root with an empty protected list and `Get-FullPath` on the same text, and prints two lines; the test compares them with `HeldDirectory.Create` on the same root. No real run is used (the script's route to a root is `-LogPath <root>\file`, which would write there). The test is a control that passes before this plan, with a staged mutation to give it teeth.
- **P-5, what the bookkeeping edits and what it leaves alone.** Register rows and validation rows are added (the orchestrator asked for them); the audit trail, counts, sign-off and frontmatter of `01-SECURITY.md`, and `01-VERIFICATION.md`, `01-UAT.md` and `01-REVIEW-DISPOSITION.md`, are not edited (the disposition row CR-01 becomes `fixed` through the review gate, which is the orchestrator's step). Line citations in the rows of T-01-51 to T-01-59 name `HeldDirectory.cs` lines at `ed8ee27`; the fix shifts the lines below it, which the next secure-phase run re-measures (flagged in the SUMMARY).
