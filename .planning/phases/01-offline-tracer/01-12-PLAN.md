<objective>
Close verification gap 2: the `--out` containment guard compares lexical paths, so an `--out` that reaches the analysed repository through a symbolic link or a directory junction is not seen as inside it and the tool writes its five files into the repository's work tree. Resolve links before comparing, in both places that guard: `CliApp.RefuseUnsafeOut` and `Test-SameOrUnder` in `scripts/trace-run.ps1`.

Purpose: roadmap criterion 2 says everything the run writes lands in `--out` and nowhere else, and the repository that was read is never changed (D-02, D-03; threat T-01-28, and T-01-26 for the trial script). The gap was reproduced on Windows in `01-VERIFICATION.md`: a junction to the repository, `--out <junction>/outx`, exit 0, `?? outx/` in `git status`. The trial script has the same weakness and one more: it writes `-LogPath` itself, so a log path through a link lands in the repository even when vdiff would refuse.

Wave note: the dependency on plan 01-11 is about the build, not about behavior. Both plans compile into the one `Vdiff.Tests` assembly and run the same `dotnet test` and sidecar fixture build, so run in the same tree a half-edited file of one plan fails the other plan's build and every gate with it. The two gaps themselves are independent and share no file.

Resolution rule (one rule, two implementations): take the full path; walk it from its root one segment at a time; when a segment is a symbolic link or a directory junction, replace everything so far by the link's final target and resolve that target by the same rule (its own ancestors can be links); stop at the first segment that does not exist and append the rest unchanged; allow at most 40 links in one resolution; any failure (a loop, an unreadable link, no access) is a refusal and never a silent fall-back to the lexical path. The C# mechanism is `FileSystemInfo.LinkTarget` (non-null marks a link, dangling links included) and `ResolveLinkTarget(returnFinalTarget: true)`. The PowerShell mechanism is `Get-Item -LiteralPath -Force` with `LinkType` (`SymbolicLink` or `Junction`) and `Target`, because `ResolveLinkTarget` does not exist in Windows PowerShell 5.1. Both mechanisms were exercised on Windows during planning on a junction, a dangling junction and a looping pair of junctions: the `FileSystemInfo` link API from PowerShell 7 (the CLI targets net10.0 and the new tests run the API there), and `Get-Item` with `LinkType` and `Target` from both PowerShell hosts.

Decision on subst drive letters and DOS 8.3 short names (recorded, not left open): they are not resolved. A link walk fixes neither, a final-path Win32 call would fix both but the PowerShell 5.1 script cannot make one without compiling code, and short-name matching differs between .NET Framework and .NET Core. The verified gap is link aliasing and every link form is covered; the residual is accepted in the threat register (T-01-39) and the SUMMARY must repeat it.

Scope boundary: `CliApp.IsSameOrUnder` stays lexical (`CliOptionsTests` calls it on non-existent paths); the resolver is a separate step in front of it. Review items about pre-existing links at the five output file names (part of WR-01's optional hardening), atomic output (IN-06) and the other warnings are outside this plan.

Hygiene rule for every link in a test: links are created outside the sandbox root (inside a `LinkScratch` directory), never point at the repository checkout or at an ancestor of the sandbox (`RepoSnapshot` and `SyntheticRepo.Dispose` enumerate recursively and recursion enters junctions), and are removed first, as links, never recursively.
