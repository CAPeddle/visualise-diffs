## Planner findings this plan relies on (measured at HEAD 1f7da07)

**How gsd-tools derives completion.** `gsd-tools requirements` has three verbs: `mark-complete`, `ready-ids` and `revert-phase`. No verb writes a Partial status, so the ACC-01 row is edited by hand. `mark-complete` is used for R-10, R-23 and ACC-02.

- `mark-complete` (`~/.claude/gsd-core/bin/lib/milestone.cjs`, cmdRequirementsMarkComplete) advances a traceability row only when its Status cell starts with the status word Pending or Gaps Found. When a row exists but the write is rejected, it rolls back the checkbox flip.
- `phase complete` (`phase.cjs` lines 6391 to 6414) uses the same status-word gate with Pending, In Progress and Gaps Found, and the same rollback. This was read from the code, not executed: a scratch-copy run stopped at the verification gate before reaching that code.
- A row whose Status cell starts with "Partial" is therefore never advanced, and neither verb ticks its checkbox. This was measured on a scratch copy. Today `mark-complete ACC-01` flips ACC-01 to [x] and Complete. After the Partial edit, `mark-complete R-10 R-23 ACC-01 ACC-02` marks only R-10, R-23 and ACC-02, and leaves ACC-01 at [ ] and Partial.
- This matters for this plan. Its `requirements` field must list ACC-01, and execute-plan's `update_requirements` step passes that field to `mark-complete`. The Partial row is what makes that call safe.

**The SUMMARY decision: edit them.** The five frontmatters of 02-02, 02-04, 02-07, 02-08 and 02-10 move ACC-01 out of `requirements-completed`, as the verifier's second `missing` item asks.
- Why: audit-milestone step 5c reads `requirements-completed` from every SUMMARY. In its 5d matrix, a verification row of passed, a SUMMARY that lists the ID and an unticked checkbox give "satisfied (update checkbox)", so the audit would re-tick ACC-01 after a passing re-verification. If no SUMMARY lists ACC-01, the matrix gives "partial (verify manually)", which is correct.
- Cost: the five SUMMARYs are in 02-VERIFICATION.md `covered_files`, so its `covered_digest` goes stale. Gap closure re-runs the verifier anyway, which regenerates the digest. 02-VERIFICATION.md is not edited by this plan.
- Checks: the `summary` frontmatter schema does not require `requirements-completed`, so an empty list still validates. `summary-extract` parses the edited form and returns an empty list (checked on a scratch copy).

**Spec-less probe fallback not run (orchestrator decision, recorded).** No phase SPEC exists. This run changes only requirement-tracking text, and 02-VERIFICATION.md already verified the phase's requirement predicates. No probe-derived predicates were generated.
