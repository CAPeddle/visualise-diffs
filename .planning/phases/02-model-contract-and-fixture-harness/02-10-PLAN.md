## Proposed conventions this plan writes into goldens (flagged; ids and member keys are the frozen Identity grammar of `docs/schema/README.md`, so Phase 4 confirms or revises only the signature text, the lane selection, the managed-wrapper stereotype and the package node, through a reviewed accept-mode update)

- C#: ids and member keys follow the Identity grammar in `docs/schema/README.md` (plan 02-05; D-21, D-22), which this fixture exercises. Language `csharp`; fqn uses `.` (`Synthetic.Orders.OrderService`); id is `<kind> <fqn>`; `scope` is the namespace, or the enclosing type's fqn for a nested type (`class Synthetic.Orders.OrderService.Receipt`). A generic type's name carries its arity as the unbound form, so `Foo` and `Foo<T>` in one namespace are `class Synthetic.Orders.Foo` and `class Synthetic.Orders.Foo<>`. A method or constructor key is the name plus the parameter list as written, whitespace collapsed (`Submit(Order order)`; overloads are told apart by the list, as `Reset()` and `Reset(int to)`; a constructor is named after its type and has kind `constructor`). A field or property key is its name. Only the signature text below is still a proposal for Phase 4 to confirm; the ids and keys are the frozen grammar. A method signature is the declaration without access keywords, attributes or body, whitespace collapsed (`bool Submit(Order order)`). A property signature is the type and the name only (`int RetryCount`), without the accessor list. Sources are idiomatic, unqualified C# (a base is written `Document`, not `Synthetic.Orders.Document`). Edge targets follow the D-16 clarification in CONTEXT.md: the Roslyn C# extractor (Phase 4) resolves a base semantically, so `to` is the resolved symbol's full id (`<kind> <fqn>`) and `to_name` is the base as written; the exact/`::`-suffix rule governs only the syntax-only C++ extractors and is not applied to C# goldens. The model's type-level `access` (D-19) is not in the diff (D-20), so no listed type in either golden carries an access, modifiers, `partial` or `files` field.
- C++/CLI: ids and member keys follow the Identity grammar in `docs/schema/README.md` (plan 02-05; D-21, D-22): language `cpp-cli`, `::` in the fqn, and the kind mapping in which `ref class` and native classes in a C++/CLI file are `class`, a `value class` is `struct`, an `interface class` is `interface` and an `enum class` is `enum`. Signatures follow the C++ sidecar's form and remain a proposal.
- Which files form the managed-wrapper lane (here the headers of a project with `<CLRSupport>true</CLRSupport>`), and the package-pin rule, become `fixture.yml` config keys only when Phase 4 adds them to the `.visualise-diffs.yml` reader.
