## Golden conventions (also written into tests/fixtures/README.md by task 2)

Goldens describe the finished tool, not today's tracer:
- Whole-repository extraction (R1, Phase 3). Unchanged types and unchanged edges in files the change did not touch are counted in `summary`.
- ModelDiffer's rules (Phase 1 D-07) apply, plus v1:
  - Types are matched by language plus id, members by key.
  - An added type lists all its members as `added` and all its bases in `bases.added`; a removed type is the mirror image.
  - A member is `modified` when its access, signature or modifiers differ, and `body-changed` when a diff hunk overlaps its span and nothing else changed (R-13).
  - Unchanged members are never listed: a type's `members` holds only members in state `added`, `removed`, `modified`, `renamed` or `body-changed`, and members have no unchanged count. This is the frozen schema's presence rule, and `DiffPresence` rejects a listed member in state `unchanged`.
  - `warnings` is empty and `unmodelled` is 0 and 0 unless a fixture intends otherwise.
- Renames (R-14). A renamed type is listed once, under its head id, with `renamed_from` and `rename`:
  - `score_milli = 500 * shared / total` (integer division) + 200 (same file or git rename pair) + 200 (same namespace) + 100 (same base set).
  - `member_jaccard` counts member names: `shared` is the intersection, `total` the union.
  - A member of a matched type is `renamed` (with `renamed_from_key`) when its parameter list and return type are identical and the pair is unique.
- Edges:
  - Identity is kind, `from`, `to_name` and `via`. Present only in head means `added`, only in base `removed`.
  - An edge whose only change is a renamed endpoint type is listed once with state `renamed` and its head-side endpoints.
  - An association edge (proposed rule; Phases 4 and 5 implement it) runs from type T to type U when a field of T is declared with a type that resolves to a modelled type U of the same language. For the syntax-only C++ extractors, resolution works like a base's (exact fqn, else a unique `::` suffix) after stripping template arguments, pointer, reference and const; per the D-16 clarification that rule is not language-universal, and the Roslyn C# extractor (Phase 4) resolves base and field types semantically, so a C# edge's `to` is the resolved symbol's full id. `via` is the field's key, and `to_name` is the type name as written. A field whose type resolves to no modelled type of the same language creates no edge; cross-language links are R17 (P2).
- Fixtures avoid the keywords `static`, `virtual`, `override`, `inline`, `explicit` and `constexpr`, so every `modifiers` list is empty whether or not an extractor fills modifiers.
- Both outputs are pending in every fixture: `diff` due 5 and `summary` due 7.

## Member keys and signatures (C++; part of the golden conventions, copied into tests/fixtures/README.md by task 2)

These are the Phase 1 sidecar rules, pinned by the sidecar's own unit tests in `extractors/cpp-ts/src/extract.rs` (for example `signatures_keep_specifiers_and_drop_bodies_initializers_and_semicolons`, `one_member_per_declarator` and `bases_drop_access_and_virtual_and_collapse_whitespace`). The finished tool keeps them, so a golden spells every key and signature by these rules and the table below (D-06):
- A method or constructor key is the name, then the parameter list as written with whitespace collapsed to single spaces, then any trailing qualifier such as ` const`: `width() const`, `Circle(double r)`, `grow(int by, long times)`.
- A field key is the field name: `height_`.
- A signature is the declaration text with whitespace collapsed, up to where a body or a constructor initialiser list starts, without the final `;`. Specifiers stay, and so do `= 0`, `= default`, `= delete` and a field's default value: `int width() const`, `void paint()`, `Circle(double r)`, `int height_ = 0`, `double radius`.
- A member diff carries no member kind, so how an extractor labels a constructor does not appear in any golden.
- Bases are the written base names with access and `virtual` dropped and whitespace collapsed: `class SYNTH_API Widget : public Component` has bases `["Component"]` once `SYNTH_API` is blanked.
- A type id is `<kind> <fqn>`, with `::` in a C++ fqn: `class synthetic::Widget`. Its `scope` is `synthetic`.
- `member_jaccard` counts member names, not keys, so a renamed constructor counts as two different names.

Worked keys and signatures for this plan's fixtures. Every member a golden lists is here. Access is `public` everywhere except Widget's `height_`, which is `protected` in base and `public` in head.

## Provisional summary format (D-07; S1 and Phase 7 may revise it through accept mode and a reviewed diff)

Built from the S1 sample (`docs/spikes/S1-mermaid-in-ado-pr.md`) with the Phase 1 conventions (`C_` class ids from 01-11, quoted labels and trailing member tags from 01-08):
1. The first line is `classDiagram`.
2. Class lines in three groups: changed types ordered by language then id; then context neighbours (R18: 1-hop bases, derived types and association targets of changed types, in either model, that are not themselves changed), ordered by language then id; then package nodes ordered by name.
3. The class id is `C_` plus the fqn with every character outside letters, digits and underscore replaced by `_`, made unique with `_2`, `_3` in line order. This is `MermaidWriter.ClassId`; `synthetic::Widget` becomes `C_synthetic__Widget`.
4. A changed type is written as two spaces, `class`, the id, `["<fqn>"]`, `:::<state>`, then ` {` when it has a block. A block holds stereotype lines, then changed member lines ordered by key, then a line of two spaces and `}`.
5. Stereotype lines are four spaces plus `<<renamed from <base name>>>` for a renamed type (first), where the base name is the unqualified name after the last `::` or `.` (as in the S1 sample, so no `::` sits inside a stereotype), and four spaces plus `<<managed wrapper>>` for a `cpp-cli` type (D-17: the lane is rendered from the language).
6. A member line is four spaces, a visibility character (`+` public, `#` protected, `-` private) taken from `access_after`, or from `access_before` for a removed member, the signature (`signature_after`, or `signature_before` for a removed member), a space and `[<state>]`. The state is one of added, removed, modified, renamed or body-changed. For example, small-cpp's removed public `paint()` renders as `    +void paint() [removed]`.
7. A context node is two spaces, `class`, the id, `["<fqn>"]` and `:::context`, with no block. A `cpp-cli` context node is the exception: its block holds only the managed-wrapper stereotype.
8. A package node is `C_package_` plus the sanitised name, labelled `package updated: <name> <old> → <new>` (U+2192) with `:::modified`. For an added package the label is `package added: <name> <new>` with `:::added`; for a removed one, `package removed: <name> <old>` with `:::removed`.
9. Edge lines are sorted ordinally as whole lines and drawn only between shown classes:
   - inheritance: two spaces, base id, ` <|-- `, derived id;
   - association: two spaces, from id, ` --> `, to id, ` : uses`, plus ` [added]` for an added edge;
   - a removed association uses ` ..> ` and ends ` : uses [removed]`;
   - a renamed edge is drawn like an unchanged one.
10. The classDef lines come last, all five, in this order:
    - the three the writer emits today (added, removed, modified);
    - `  classDef renamed fill:#e0ecff,stroke:#1565c0,color:#111`;
    - `  classDef context fill:#eeeeee,stroke:#9e9e9e,color:#666`.
11. LF line ends and one trailing LF.
