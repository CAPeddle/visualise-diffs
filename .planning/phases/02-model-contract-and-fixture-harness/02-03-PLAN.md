## Contract tables (authoritative; plan 02-05 transcribes them into schema; plan 02-12 implements the diff table)

Rules for every table:
- Declaration order of the record's positional parameters is the JSON key order (snake_case via `JsonNamingPolicy.SnakeCaseLower`).
- `?` marks a nullable property. It is omitted from JSON when null and is not in the schema's `required` list. Every other property is required, and lists are always written, even when empty.
- `code` means a string matching `^[a-z][a-z0-9-]*$`.
- `lang` is the enum `cpp | csharp | cpp-cli`.
- `access` is the enum `public | protected | private | internal | protected-internal | private-protected | none`. The member access, the type-level access (D-19) and the diff's `access_before`/`access_after` fields all use this one enum, so the schema enums stay identical. The value `none` is legal for a member only: a type-level access (and a `TypeDiff` access pair) never holds it (see the type rules).

Edge resolution is not part of these tables (D-16 clarification). The tables fix the edge shape: `from`, `to` present only when the extractor resolved `to_name` to one modelled type, `to_name` as written. How `to` is resolved belongs to each extractor. The syntax-only C++ extractors (the tracer and the tree-sitter sidecar) use the exact/`::`-suffix rule in `BaseResolver.Resolve`, and the Roslyn C# extractor (Phase 4) resolves semantically and sets `to` to the resolved symbol's full id.

Type rules (D-19), which the schema descriptions document. The draft-07 subset cannot express them, so the test-side checker `ModelPresence.Problems(ModelFile)` (plan 02-05, task 3) enforces each one with its own negative row, and runs clean on `ContractSamples` and on the tracer's real models:
- `access` is the type's declared accessibility, or the language default where the language has one (C#: `internal` at namespace scope, `private` when nested). It is absent when the extractor has no type-level access: C++ types at namespace scope have none, and the tracer omits it on every type because the sidecar protocol v0 reports none.
- `none` is not a legal type-level `access` value. Absence is the only encoding of "no type-level access", so the differ, which compares a null access as a value of its own, can never report a spurious `modified` between `none` and absent. The schema reuses the member enum (where `none` stays legal) to keep enum parity, so `ModelPresence` enforces this restriction rather than a schema keyword.
- `partial` is true only for a type declared in parts (C# `partial`), false otherwise. C++ has no partial types, so the tracer writes false. A required boolean keeps one encoding for "not partial".
- `files` is present exactly when `partial` is true: every repository-relative file that declares a part of the type, sorted ordinally, without repeats (a one-file partial type lists its one file). `file` is the first entry of `files`, and `span` is the span of the earliest part in that file, so a partial type's `file` and `span` do not depend on the order in which an extractor visits its parts (R-23).
- Open item for the 02-06 freeze review, not added here: `MemberModel` has no file, so a member declared in another part of a partial type cannot be placed in its file from the model alone. An optional member `file` would be an additive change inside v1.

Presence rules, which the schema descriptions document and tests enforce (draft-07 subset, no `if/then`, D-15):
- A `MemberDiff` `*_before` field is present exactly when the member exists on the base side, and `*_after` exactly when it exists on the head side. This applies to access, signature and modifiers alike.
- `TypeDiff.BaseFile` is present when the base side exists, and `HeadFile` when the head side exists.
- `TypeDiff.AccessBefore` and `AccessAfter` (D-19) are change-only, unlike the member pair: both are absent unless the type exists on both sides and its type-level access differs between them. Then each holds that side's access and is absent when that side has none. Neither ever holds `none`: absent is the only encoding, as in the model.
- Type state precedence (D-19 with D-02): a type matched by language and id whose access differs is `modified`; a type matched by rename (Phase 5) stays `renamed` whatever else changed, access included, so `renamed` wins over `modified`. The access pair may therefore appear on a type in state `renamed` or `modified` and on no other state. Those are the two listed states in which the type exists on both sides, so `base_file` and `head_file` are both present whenever the pair is. The rule can be checked from `diff.json` alone (state `renamed` or `modified`, the two values never equal, neither `none`), whereas a per-side rule copied from `MemberDiff` would depend on whether the model's optional `access` was filled. `partial` and `files` are not compared: a part added to, moved between or removed from files does not change a type's state, and `BaseFile`/`HeadFile` carry the model's `file`.
- `RenamedFrom` and `Rename` are present only for state `renamed`. `RenamedFromKey` is present only for member state `renamed`.
- `PackageDiff.OldVersion` is present for `updated` and `removed`, and `NewVersion` for `updated` and `added`.
- Unchanged types and unchanged edges are counted, never listed.
- Unchanged members are never listed, and they have no count (`MemberCounts` has no `Unchanged`). A type's `members` holds only members in state `added`, `removed`, `modified`, `renamed` or `body-changed`. The `MemberDiff.State` and `TypeDiff.State` enums keep `unchanged` for symmetry with D-02 (RESEARCH "Proposed v1 Shapes": in the enums, never listed in v1); `EdgeDiff.State` has no `unchanged` value. The Phase 1 differ already lists only changed members.
- `ScoreMilli` is `500 * shared / total` (integer division, rounded down; 0 when total is 0) + 200 for same file or git rename pair + 200 for same namespace + 100 for same base set. The R-14 threshold is 600.
