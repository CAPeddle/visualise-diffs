# ADR-001: Package the C++ tree-sitter extractor as a native sidecar

- **Status:** Accepted (PO, 2026-11-16)
- **Date:** 2026-11-16
- **Spike:** S2 (plan U3). Related requirements: R5, R9, R10, R23, R26; decision D14.

## Context

`vdiff` is a C#/.NET 10 CLI with Roslyn in-process. Its C++ extractor parses syntax only, with
tree-sitter, after a pre-pass that blanks configured macros without changing the length of the
text (R5). Every extractor emits the versioned `vdiff-model/v1` JSON (R10, D14). Source spans
must stay valid after blanking. Output must be byte-identical for identical input (R23). The job
runs on Ubuntu by default and on Windows as the fallback (R26), with a 20-minute hard limit.

The question is how to package the extractor:

- **A.** A .NET tree-sitter binding, called in-process from C#.
- **B.** A native Rust sidecar (`tree-sitter` 0.27.0 + `tree-sitter-cpp` 0.23.4), run as a
  subprocess that prints JSON on stdout.

An earlier private trial of B, with exactly these crate versions, parsed a real C++ codebase
successfully with a length-preserving macro-blanking pre-pass and rayon. B is therefore known to
work. This spike adds a like-for-like comparison on synthetic code only. No numbers from the
private trial are used here.

Only `TreeSitter.DotNet` was inspected in depth (package contents, nuspec, repository, and the

"A" below means `TreeSitter.DotNet` 1.3.0.

### A. In-process binding

The package carries about 28 grammars for every RID. A framework-dependent
`dotnet publish -r linux-x64` copies all of them next to the app. The API is string-based:
`Parser.Parse(string)` is the only parse entry point, and offsets and columns are UTF-16 code
units. The bundled core and grammar versions are chosen by the binding's maintainer.

### B. Rust sidecar

`tree-sitter` and `tree-sitter-cpp` come from crates.io and are pinned by `Cargo.lock`.
`Parser::parse` takes a byte slice, so the pre-pass works on the raw file bytes and offsets are
byte offsets in the file. The orchestrator starts the binary, reads JSON from stdout, and
validates it against `vdiff-model/v1`.

## Evidence

(0.85 MB) and 2000 files (8.5 MB). Each file has 2 to 5 classes or structs with access sections,

`EXPORT_API`-style macro on 60% of the type heads. Comments contain non-ASCII text. The 200-file
corpus yields 1432 type specs and 7865 members; the 2000-file corpus yields 13948 and 76452

Notes on the evidence:

- **Speed does not decide this.** Both options finish a 2000-file repository in well under a
  second with 16 threads, against a 5-minute P90 target (R26). B is faster, mostly at 16 threads
  (about 2x), but A's number includes a per-type UTF-8 offset conversion that starts at offset 0
  each time. With that conversion off (`--latin1`) A took 236 ms on 2000 files at 16 threads
  (Windows), against 242 - 258 ms with it, so the conversion is not the main cost either.
- **Size barely discriminates after pruning.** A ships 65 - 69 MB of grammars nobody needs unless
  a post-publish step deletes them. Pruned, it is 5.7 MB against B's 4 MB.
- **Blanking matters.** Without it, about 465 of 1432 types are lost, because the parser reads
  `class EXPORT_API Name` with the macro in the name position. With it, every type is found.
  This holds in both options.
- **Start-up cost of the subprocess is small on Linux.** B starts in about 6 ms. The Windows
  start-up figures taken from Git Bash (170 ms for B on an empty directory) measure shell and
  antivirus overhead and are not used.
- **Windows A console output.** A's JSON came out mojibake'd when written to a redirected console
  on Windows with the default code page. The sidecar must write UTF-8 explicitly in either
  option. Not a binding fault.

### Macro blanking and spans in each option

The pre-pass is a byte-level or character-level scan that replaces each whole-word macro name
with the same number of spaces, skipping preprocessor lines.

- **B:** `parser.parse(&bytes, None)` takes the file bytes after the pass. Node offsets are byte
  offsets in the original file, columns are byte columns, and no decoding step exists. The pass
  is about 40 lines. Nothing drifts.
- **A:** `Parser.Parse(string)` only. The file must first become a string, and offsets and
  columns come back in UTF-16 code units. Two ways to get valid spans:
  1. Decode as UTF-8, blank, parse, and convert each offset to UTF-8 bytes. This worked on the
     clean corpus (identical to B). It drifts when the file has a BOM, an invalid UTF-8 byte, or a
     legacy code page (Windows-1252 is common in older C++ trees), as measured above. A fix would
     decode with a byte-preserving scheme and keep the BOM.
  2. Decode every byte as one Latin-1 character, so UTF-16 offsets equal byte offsets. This gave
     exact spans, including with a BOM or Latin-1 comment. It fails silently on non-ASCII
     identifiers: the parser dropped both test classes with no error. That contradicts R9
     ("never present partial extraction as complete") unless error nodes are counted and
     reported.

  Neither is hard, but both are workarounds for an API that cannot take raw bytes.

### Determinism (R23)

- With clean (blanked) input, A and B produced identical output on both operating systems and at
  1, 4 and 16 threads. Results are written in the sorted file order, never in completion order.
- On input the grammar cannot parse cleanly, tree-sitter's error recovery depends on the core and
  grammar versions. A (core 0.26.3, `tree-sitter-cpp` from 2025-09-27) and B (0.27.0, tag
  v0.23.4) disagreed on 8 types when blanking was off. The version pair is therefore part of the
  output contract. In B, `Cargo.lock` fixes it. In A, the binding's maintainer chooses it and a
  package update changes it, and an unreleased grammar commit cannot be pinned by us.
- The model metadata should record the tree-sitter core and grammar versions, and the count of
  error nodes per file, so a change in either shows up as a labelled difference, not a silent one.

### Subprocess cost and complexity for B

- Start-up is about 6 ms on Linux, so one subprocess per run (not per file) is cheap. The sidecar
  takes a file list or root and writes one JSON document to stdout.
- The orchestrator needs a timeout and an output-size bound, a non-zero exit mapped to "files not
  modelled" under R9, and a schema check of the JSON. D14 already requires the JSON contract for
  every extractor, so this is not a cost that only B pays.
- A crash or runaway parse in native code stays inside the child process. In A the same fault
  takes down the Roslyn side and the whole run.
- B adds a second toolchain (Rust and a C compiler), a per-RID build and release matrix (at least
  linux-x64 and win-x64 for R26; osx-arm64 only if needed), and version tracking for two crates.
  Rust was not tested on osx-arm64, on musl, or with a static C runtime on Windows (the Windows
  runtime dependency is unverified).

## Decision

Use **B**, a native Rust sidecar with `tree-sitter` 0.27.0 and `tree-sitter-cpp` 0.23.4, pinned
by `Cargo.lock`, invoked once per run as a bounded subprocess that emits `vdiff-model/v1` JSON on
stdout.

The deciding facts are:

1. **Spans.** B parses the raw bytes, so offsets are exact for any file encoding with no
   workaround. A's API takes only a string and indexes in UTF-16, so exact spans need either an
   offset conversion that drifts on BOMs and legacy encodings, or a Latin-1 trick that silently
   drops types with non-ASCII identifiers. R5 and R9 make both a risk.
2. **Version control.** B uses released crates at the versions the plan names, locked in the
   repository. A wraps one maintainer's bundle, with an unreleased grammar commit and a core one
   minor version behind, and any package update can change error-recovery output (R23).
3. **Isolation.** Native parser faults and timeouts are contained in a child process.
4. **Maintenance of the binding.** `TreeSitter.DotNet` is current and works, but it has one
   maintainer, and the other bindings in the survey are stale or unverified.

Size and speed do not decide it. A is the better choice only if the team cannot take on a Rust
toolchain and a per-RID release matrix. In that case use `TreeSitter.DotNet` with a pinned
version, a byte-preserving decode, error-node counting, and a post-publish prune of unused
grammars. The trial shows it produces identical output on clean input.

## Consequences

- The repository gains a Rust crate (suggested path `extractors/cpp-ts/`) with `Cargo.lock`
  checked in. CI builds and publishes `linux-x64` and `win-x64` binaries, and the .NET side finds
  the binary by RID next to `vdiff`.
- The sidecar's JSON schema is `vdiff-model/v1`. Spans are UTF-8 byte offsets plus 1-based start
  and end lines. The diff hunks are line-based, so lines are the units that matter for joining
  changes to types. Columns, if needed, are byte columns and documented as such.
- The sidecar records the core version, grammar version, macros blanked, and per-file error-node
  count in the extraction metadata (R9, R23). Files with error nodes are labelled, not hidden.
- U3's work splits into the sidecar crate, the blanking pass, and the orchestrator's process
  wrapper (timeout, size bound, exit-code mapping, schema validation).
- The glibc floor of the Linux binary is 2.34 when built on a current Ubuntu image. For older
  agents, build in an older image. A musl build and osx-arm64 are not verified.
- The decision is reversible. The model contract hides the packaging, so A can replace B behind
  the same JSON, and the synthetic corpus and the parity check below remain a regression test for
  either choice.
- If the grammar gap matters later (C++ features newer than v0.23.4), moving to a newer
  `tree-sitter-cpp` release is a `Cargo.toml` change plus a fixture re-baseline.

## Not verified

- Licence, core version and grammar contents of every binding except `TreeSitter.DotNet`.
- `TreeSitter.DotNet` on osx-arm64 (the binaries are in the package, never run). B on osx-arm64
  and musl, and B's Windows runtime dependencies.
- Anything on an older Linux image than Ubuntu with glibc 2.43.
- Timing on any corpus other than the synthetic one, or on hardware other than the one machine
  described above. WSL2 numbers are not native Linux numbers.
- The Latin-1 path on a wider set of non-ASCII source than the two test classes.

## Trial reproduction

The trial source is in [`docs/spikes/S2-trial/`](../spikes/S2-trial/): about 70 lines of
Python (corpus generator), 150 lines of Rust and 110 lines of C#. Generated corpora and build
outputs are not committed; regenerate them with the seeded generator.

Layout: `gen/gen_corpus.py`, `A/` (net10.0 console, one package reference
`TreeSitter.DotNet` 1.3.0), `B/` (Cargo project, `tree-sitter = "=0.27.0"`,
`tree-sitter-cpp = "=0.23.4"`, `rayon`, `serde_json`, release profile `lto = true`,
`codegen-units = 1`, `strip = true`).

Commands:

```
# corpus (seeded, deterministic)
python gen/gen_corpus.py corpus200 200
python gen/gen_corpus.py corpus2000 2000

# A: build, run, publish
dotnet build A -c Release
A/bin/Release/net10.0/s2a corpus200 --blank EXPORT_API --threads 16 > a.json
dotnet publish A -c Release -r linux-x64 --self-contained false -o pub/A-fd-linux-x64
dotnet publish A -c Release -r linux-x64 --self-contained true  -o pub/A-sc-linux-x64

# B: build, run
cargo build --release --locked --manifest-path B/Cargo.toml
B/target/release/s2b corpus200 --blank EXPORT_API --threads 16 > b.json

# parity (blanking on): the hashes must match
sha256sum a.json b.json

# Linux: copy the corpus, B sources and the published A to a WSL home directory, then
cargo build --release --locked
dotnet A-fd/s2a.dll corpus200 --blank EXPORT_API
```

Both programs follow the same rules. They walk the tree and, for every `class_specifier` or
`struct_specifier` that has a `body` and a `name`, emit the name, the `base_class_clause` entries
(access keyword and `virtual` dropped), the count of direct body children of kinds
`field_declaration`, `function_definition`, `declaration`, `template_declaration` and
`alias_declaration`, and the number of those that contain a nested class, struct or enum. Spans are
UTF-8 byte offsets. Files are listed with `*.h`, `*.hpp`, `*.cc`, `*.cpp`, sorted by ordinal path.

The two parse calls differ only in their input:

```
// A (C#): string in, UTF-16 offsets out
using var tree = parser.Parse(text);          // text = blanked string
// n.StartIndex is a UTF-16 index; convert with Encoding.UTF8.GetByteCount(...)

// B (Rust): bytes in, byte offsets out
let tree = parser.parse(&bytes, None).unwrap(); // bytes = blanked Vec<u8>
// n.start_byte() is the file offset
```

The blanking pass, in both: for each line whose first non-blank character is not `#`, replace each
whole-word occurrence of a configured macro name with the same number of spaces.
